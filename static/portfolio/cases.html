旗舰项目案例剖析

面试官最爱追问的三个问题：业务从哪来、难点怎么破、效果怎么量。这三个案例逐一回答。

问数 ChatBI · 智能问数平台

12 节点 LangGraph Text2SQL Agent · Qdrant + ES 双索引 · FastAPI SSE 流式

旗舰案例

业务背景与需求来源

业务人员看数据的日常是「提需求 → 排期 → 等数仓 → 拿报表」，一个简单问题往往要等一两天。市面上的通用问数工具能聊天，但生成的 SQL 经常找错表、配错关联，答案错了也没人发现。需求很明确：让业务人员用自然语言直接问到正确的数，并且答错能在执行前被兜住。

系统架构

▲ 问数 ChatBI 数据流：SSE 入口 → 12 节点状态图 → 双索引 / 数据库，全程流式返回

关键难点与解决思路

🧭
难点 1：LLM 不知道数据库里有什么

解法：Schema Linking 节点前置。用 Qdrant + Elasticsearch 双索引 + bge embedding 把表名、字段名、注释向量化，提问时先检索出最相关的表结构再喂给 LLM，从源头减少「找错表」。

🛡️
难点 2：生成的 SQL 会错且没人发现

解法：静态校验节点兜底。执行前检查是否为只读 SELECT、是否含危险操作、LIMIT 是否缺失、关联表是否都经过 linking 命中，不达标就打回重生成或转澄清提问。

⚡
难点 3：整段生成等待时间长

解法：FastAPI SSE 流式输出。总结阶段按 token 推送，用户看到第一个字从几十秒降到几百毫秒；SQL 与引用随结果一起返回，可核对。

🔑
难点 4：演示环境没有 LLM Key

解法：登录门禁 + 演示模式双轨。无 Key 时走规则引擎演示链路，界面与交互完全一致，保证任何时间打开都能演示；有 Key 时自动切真实 LLM。

测试结果与数据

12LangGraph 节点
2检索引擎（Qdrant+ES）
4道静态校验规则
ms 级首 token 流式延迟

用课程 30 集知识体系自建的测试问句集逐条过：schema linking 命中后生成正确率显著高于直接喂全量 schema；常见单表 / 双表问句全部跑通，答案附带 SQL 与结果表。

已知边界与迭代计划

⚠️
边界

复杂多表关联（3 表以上 + 子查询）仍会出错；自然语言有歧义时必须增加澄清轮次；方言 / 黑话问句覆盖有限。

🗺️
迭代

建设 Few-shot 示例库按问题类型路由；引入执行计划解释节点；用 Ragas 对问数准确率做量化评测并沉淀报告。

融界 · 四合一 AI 融合工作台

单端口聚合 36 个 API · LLM 双链路自动降级 · 功能零改动合并

旗舰案例

业务背景与需求来源

四个项目（RAG 智库、合同审批、智能客服、运营助手）各自独立部署，带来四个入口、四份环境、四次运维。演示时要来回切换窗口，面试官问「这几个什么关系」只能口头解释。需求：合成一个单端口工作台，功能一个不丢，演示一次全看到。

系统架构

▲ 融界工作台：登录门禁 → 单端口 36 API → 四模块复用三大引擎，LLM 双链路兜底

关键难点与解决思路

🧩
难点 1：合并不能丢功能

解法：先建工具链再动手。静态核对脚本比对 JS 引用的 75 个元素 id、65 个 class、图标符号与 HTML 定义；DOM mock 测试驱动真实代码路径跑 18 项登录断言。改完全绿才提交，旧功能零回退。

🔌
难点 2：四套系统共用一个端口

解法：模块化路由 + 统一响应结构。各模块 API 挂独立前缀，静态资源分目录托管；LLM 健康徽章启动兜底刷新，避免页面停在「检测中」。

🪫
难点 3：LLM Key 会过期 / 限流

解法：双链路自动降级。主链路（SiliconFlow）异常时切备用（阿里百炼），都不可用走演示模式规则引擎，界面交互不变，服务不中断。

🔐
难点 4：公开演示要可控

解法：内存制登录门禁。每次打开先登录（手机六位随机验证码自动填入 / 微信 / 支付宝扫码），刷新需重登——演示环境不落敏感态，符合「显式可控」原则。

测试结果与数据

36个 REST API
75个元素 id 零改动
18项登录逻辑断言
3端部署（Git/云/服务器）

合并后五视图（总览 / 智库 / 合同 / 小二 / 运营）全部可用，端点全 200；云端演示链接与服务器 :8091 双轨在线，代码开源至 GitHub。

已知边界与迭代计划

⚠️
边界

单服务器 1.7G 内存，多模块同时跑重任务需留意资源调度；子模块共用端口，故障隔离靠进程级重启。

🗺️
迭代

模块按需懒加载降低常驻内存；补自动化回归脚本覆盖五视图核心路径；把演示模式规则引擎扩展到更多模块。

罗盘 · 医药智能体

DeepAgents / LangGraph 多子代理 · MySQL + RAGFlow + Tavily 三通道 · LLM 多链路降级

旗舰案例

业务背景与需求来源

医药场景的数据天然分裂：药品 / 库存 / 销量在 MySQL 三张表里，产品知识在内部文档里，政策与竞品动态在互联网上。业务方问一句「XX 药最近卖得怎么样、库存还够吗、有没有新政策」，原来要查数据库、翻文档、搜网页三处手工汇总。需求：一个智能体把三处数据源缝合成一个入口。

系统架构

▲ 罗盘医药智能体：主智能体按意图分发三个子代理，LLM 多链路兜底

关键难点与解决思路

🧠
难点 1：问题该问数据库还是问文档？

解法：主智能体先做意图判断再分发子代理——带「库存 / 销量 / 记录」等数据词走 DB 子代理，带「说明 / 禁忌 / 政策」走知识子代理，时事类走搜索子代理；混合问题多代理并行后汇总。

🧯
难点 2：RAGFlow 服务偶发不可用

解法：熔断降级。知识子代理探测到 RAGFlow 无响应时自动切本地 FTS5 检索通道，并在回答里标注「知识库降级」，用户知情、服务不崩。

🔗
难点 3：LLM 链路说挂就挂

解法：双 LLM 后端 + 健康探测。主链路超时 / 报错自动切备用链路，全部不可用走演示模式，三种状态界面一致。

💾
难点 4：多轮追问上下文不能丢

解法：会话与历史记录持久化，子代理之间通过结构化消息传递中间结果，避免上下文互相污染。

测试结果与数据

3个数据通道自动路由
3张核心业务表
2条 LLM 链路互备
0次服务中断（降级后）

用药品库存查询、销售排行、政策咨询三类典型问句回归：路由正确率与回答可溯源率均达预期；模拟 RAGFlow 挂断与 LLM 超时，降级链路自动接管，界面无感知。

已知边界与迭代计划

⚠️
边界

多表关联查询依赖 schema 描述质量，表关系复杂时需人工补注释；联网搜索结果时效性与可信度需在回答中标注。

🗺️
迭代

引入 Ragas 对检索命中与回答忠实度做量化评测；建设问句回归集持续跟踪路由正确率；补充医药实体识别提升问句解析。
