旗舰案例

业务背景与需求来源

业务人员看数据的日常是「提需求 → 排期 → 等数仓 → 拿报表」，一个简单问题往往要等一两天。市面上的通用问数工具能聊天，但生成的 SQL 经常找错表、配错关联，答案错了也没人发现。需求很明确：让业务人员用自然语言直接问到正确的数，并且答错能在执行前被兜住。

系统架构

▲ 问数 ChatBI 数据流：SSE 入口 → 12 节点状态图 → 双索引 / 数据库，全程流式返回

关键难点与解决思路

🧭
难点 1：LLM 不知道数据库里有什么

解法：Schema Linking 节点前置。用 Qdrant + Elasticsearch 双索引 + bge embedding 把表名、字段名、注释向量化，提问时先检索出最相关的表结构再喂给 LLM，从源头减少「找错表」。

🛡️
难点 2：生成的 SQL 会错且没人发现

解法：静态校验节点兜底。执行前检查是否为只读 SELECT、是否含危险操作、LIMIT 是否缺失、关联表是否都经过 linking 命中，不达标就打回重生成或转澄清提问。

⚡
难点 3：整段生成等待时间长

解法：FastAPI SSE 流式输出。总结阶段按 token 推送，用户看到第一个字从几十秒降到几百毫秒；SQL 与引用随结果一起返回，可核对。

🔑
难点 4：演示环境没有 LLM Key

解法：登录门禁 + 演示模式双轨。无 Key 时走规则引擎演示链路，界面与交互完全一致，保证任何时间打开都能演示；有 Key 时自动切真实 LLM。

测试结果与数据

12LangGraph 节点
2检索引擎（Qdrant+ES）
4道静态校验规则
ms 级首 token 流式延迟

用课程 30 集知识体系自建的测试问句集逐条过：schema linking 命中后生成正确率显著高于直接喂全量 schema；常见单表 / 双表问句全部跑通，答案附带 SQL 与结果表。

迭代计划

🗺️
迭代

建设 Few-shot 示例库按问题类型路由；引入执行计划解释节点；用 Ragas 对问数准确率做量化评测并沉淀报告。

融界 · 四合一 AI 融合工作台

单端口聚合 36 个 API · LLM 双链路自动降级 · 功能零改动合并

旗舰案例

业务背景与需求来源

四个项目（RAG 智库、合同审批、智能客服、运营助手）各自独立部署，带来四个入口、四份环境、四次运维。演示时要来回切换窗口，面试官问「这几个什么关系」只能口头解释。需求：合成一个单端口工作台，功能一个不丢，演示一次全看到。

系统架构

▲ 融界工作台：登录门禁 → 单端口 36 API → 四模块复用三大引擎，LLM 双链路兜底

关键难点与解决思路

🧩
难点 1：合并不能丢功能

解法：先建工具链再动手。静态核对脚本比对 JS 引用的 75 个元素 id、65 个 class、图标符号与 HTML 定义；DOM mock 测试驱动真实代码路径跑 18 项登录断言。改完全绿才提交，旧功能零回退。

🔌
难点 2：四套系统共用一个端口

解法：模块化路由 + 统一响应结构。各模块 API 挂独立前缀，静态资源分目录托管；LLM 健康徽章启动兜底刷新，避免页面停在「检测中」。

🪫
难点 3：LLM Key 会过期 / 限流

解法：双链路自动降级。主链路（SiliconFlow）异常时切备用（阿里百炼），都不可用走演示模式规则引擎，界面交互不变，服务不中断。

🔐
难点 4：公开演示要可控

解法：内存制登录门禁。每次打开先登录（手机六位随机验证码自动填入 / 微信 / 支付宝扫码），刷新需重登——演示环境不落敏感态，符合「显式可控」原则。

测试结果与数据

36个 REST API
75个元素 id 零改动
18项登录逻辑断言
3端部署（Git/云/服务器）

合并后五视图（总览 / 智库 / 合同 / 小二 / 运营）全部可用，端点全 200；云端演示链接与服务器 :8091 双轨在线，代码开源至 GitHub。

迭代计划

🗺️
迭代

模块按需懒加载降低常驻内存；补自动化回归脚本覆盖五视图核心路径；把演示模式规则引擎扩展到更多模块。

罗盘 · 医药智能体

DeepAgents / LangGraph 多子代理 · MySQL + RAGFlow + Tavily 三通道 · LLM 多链路降级

旗舰案例

业务背景与需求来源

医药场景的数据天然分裂：药品 / 库存 / 销量在 MySQL 三张表里，产品知识在内部文档里，政策与竞品动态在互联网上。业务方问一句「XX 药最近卖得怎么样、库存还够吗、有没有新政策」，原来要查数据库、翻文档、搜网页三处手工汇总。需求：一个智能体把三处数据源缝合成一个入口。

系统架构

▲ 罗盘医药智能体：主智能体按意图分发三个子代理，LLM 多链路兜底

关键难点与解决思路

🧠
难点 1：问题该问数据库还是问文档？

解法：主智能体先做意图判断再分发子代理——带「库存 / 销量 / 记录」等数据词走 DB 子代理，带「说明 / 禁忌 / 政策」走知识子代理，时事类走搜索子代理；混合问题多代理并行后汇总。

🧯
难点 2：RAGFlow 服务偶发不可用

解法：熔断降级。知识子代理探测到 RAGFlow 无响应时自动切本地 FTS5 检索通道，并在回答里标注「知识库降级」，用户知情、服务不崩。

🔗
难点 3：LLM 链路说挂就挂

解法：双 LLM 后端 + 健康探测。主链路超时 / 报错自动切备用链路，全部不可用走演示模式，三种状态界面一致。

💾
难点 4：多轮追问上下文不能丢

解法：会话与历史记录持久化，子代理之间通过结构化消息传递中间结果，避免上下文互相污染。

测试结果与数据

3个数据通道自动路由
3张核心业务表
2条 LLM 链路互备
0次服务中断（降级后）

用药品库存查询、销售排行、政策咨询三类典型问句回归：路由正确率与回答可溯源率均达预期；模拟 RAGFlow 挂断与 LLM 超时，降级链路自动接管，界面无感知。

迭代计划

🗺️
迭代

引入 Ragas 对检索命中与回答忠实度做量化评测；建设问句回归集持续跟踪路由正确率；补充医药实体识别提升问句解析。

灵犀 · RAG 智能智库

FTS5 中文二元分词 · 答案强制引用溯源 · 无 Key 演示双模式

业务背景与需求来源

企业知识散落在各岗位的文档里，通用大模型回答私有文档幻觉严重、无法溯源。需求：把文档变成可检索、可引用、随时可演示的私有知识库，且不引入向量库的运维负担。

核心流程

▲ 灵犀 RAG 数据流：从文档上传到带引用问答的五步闭环

关键难点与解决思路

✂️
难点 1：FTS5 默认分词对中文失效

解法：自研二元分词双侧展开——索引与查询两侧用同一套切分逻辑，「企业经营分析」搜「经营分析」也能命中，中文检索命中率显著提升。

🔗
难点 2：答案不可溯源 = 幻觉没证据

解法：问答结果强制附带原文引用片段，用户可点击核对；检索未命中时明确回答「知识库中未找到」，不让模型硬编。

🪫
难点 3：演示环境没有 LLM Key

解法：双模式设计——有 Key 走 LLM 增强问答，无 Key 走演示模式，界面与交互完全一致，保证随时可演示。

测试结果与数据

100%答案可溯源
2元分词切词
0向量库依赖
2种模式（有/无 Key）

迭代计划

🗺️
迭代

补充 PDF / Word 多格式解析；长文档分层分块策略；引入 Ragas 对检索命中与回答忠实度做量化评测。

电商小二 · AI 客服管家

三轨对话引擎 · 6 套业务 flow · 防幻觉白名单 · 会话持久化

业务背景与需求来源

电商客服 80% 是重复问题，通用客服机器人答非所问，甚至幻觉出无法兑现的承诺（「这单我给您免了」）。需求：一个按业务 flow 走、承诺有人把关、多轮上下文不丢的客服系统。

核心流程

▲ 电商小二三轨对话引擎：意图路由分流，白名单校验后才回复

关键难点与解决思路

🧭
难点 1：一句话该走哪条业务线

解法：LLM 意图路由 + flow 配置驱动。task / knowledge / chitchat 三轨分流，6 套业务流程写成配置，加业务不改代码。

🛡️
难点 2：模型会「好心」承诺做不到的事

解法：防幻觉白名单校验——涉及退款、赔偿等敏感承诺的关键词与动作，生成后过白名单，不匹配则拦截转人工话术。

💾
难点 3：多轮对话上下文不能丢

解法：dialogue_states 表以 sender_id 为主键 + state_json 存会话状态，刷新页面后多轮上下文完整恢复。

测试结果与数据

3轨对话引擎
6套业务 flow
100%演示订单可跑通
刷新后上下文不丢

迭代计划

🗺️
迭代

flow 配置可视化编辑器；接入真实订单 API；人工接管无缝切换通道。

驾驶舱 · AI 电商运营助手

FastAPI + Celery + LangGraph + Next.js · 4 个预置 Agent · Docker 五服务编排

业务背景与需求来源

运营看数据要跨多个后台手工拉表，经营分析滞后；想让 AI 真正进入日常工作流，而不是一个聊天玩具。需求：商品店铺管理 + 经营看板 + AI Agent 分步执行一体的运营工作台。

系统架构

▲ 运营助手架构：Next.js → FastAPI → Celery → LangGraph Agent → 数据看板

关键难点与解决思路

🐳
难点 1：五服务环境一致性

解法：Docker Compose 偏移端口编排（3309/6380/5434/8002/3000），避开宿主机已占端口；数据卷持久化，环境可复现。

🤖
难点 2：Agent 执行过程是个黑盒

解法：4 个预置 Agent（信息完整度 / 广告建议 / 评价分析等）按节点分步执行，每步状态可见，结果可回放。

🪫
难点 3：Celery on Windows 进程池必崩

解法：切 solo 进程池 + 唯一节点命名，根治 SpawnPoolWorker PermissionError 与同名 worker 截胡任务两个连环坑。

测试结果与数据

4个预置 Agent
5服务一键编排
分步执行全程可视
偏移端口零冲突

迭代

法眼 · AI 合同智审平台

数据驱动规则引擎 + LLM 语义研判 · 全程审计日志

业务背景与需求来源

合同审查靠人工逐条看，风险条款漏检、审批流转无记录、出问题无法回溯。需求：机器可查条款秒级过检 + 语义风险人工聚焦 + 全程留痕可审计。

核心流程

▲ 法眼合同智审：规则引擎 + LLM 双通道，审批全程留痕

关键难点与解决思路

⚙️
难点 1：审查规则因行业 / 因企业而异

解法：数据驱动规则引擎——keyword / regex / absence / custom 四种匹配模式，11 条内置规则存数据库，加规则不改代码。

🧠
难点 2：机器规则查不了语义风险

解法：规则 + LLM 双通道。机器可查条款（金额、期限、缺席条款）秒级过检；语义风险（权责失衡、表述模糊）交 LLM 研判，人工复核兜底。

📋
难点 3：审批流转要可回溯

解法：全程审计日志——每一次审查、决定、评论、导出都记录操作人与时间点，满足合规审查。

测试结果与数据

4种匹配模式
11条内置规则
秒级机器条款过检
全程审计留痕

省身 · 企业问题自检平台

AI 抽题 · 翻卡自检 · 自研 SRS 间隔重复 · 297 项回归全绿

业务背景与需求来源

企业内审培训靠人工出题抽检：出题慢、题目无沉淀、复习没有节奏安排，检完就忘。需求：文档变题库、自检成习惯、复习按遗忘曲线走的闭环平台。

核心流程

▲ 省身闭环：文档 → 题库 → 自检 → 间隔重复复习 → 薄弱报告

关键难点与解决思路

🧠
难点 1：复习节奏怎么排

解法：自研 SRS 间隔重复算法——按答题表现为每道题计算下次复习时间，把「检完就忘」变成按遗忘曲线主动回顾。

✅
难点 2：26 项功能不能越改越坏

解法：297 项回归用例全绿才封版 v2，每轮改动先跑回归；老功能只迁移不删除（如 26 项文档抽题迁入 quiz.html）。

📄
难点 3：抽题质量依赖文档结构

解法：抽题前先做文档结构化解析，按章节 / 条款切分；低质量片段标注待人工确认，不硬出题。

测试结果与数据

26项功能封版 v2
297项回归用例全绿
4步自检闭环
SRS自研复习算法
